# 详细报告与综合对比工具

> QTest 0.3.0 · 模板 v3 · 机器报告格式 qtest-report-1 · 综合数据格式 qtest-comparison-2  
> 本次更新不改变既有 v1 测试算法，兼容 0.1.0、0.2.0、0.2.1 和 0.3.0 的原始运行证据。0.3.0 增加协作式取消状态；取消的重复实验保留证据但不计分。

## 1. 输出报告的结构

新版单机报告提供八部分：

1. **执行摘要**：项目数、计划重复、完成、不支持、失败、超时和跳过；完成状态与质量达标明确区分。
2. **设备与来源**：设备、适配器、软件依赖、执行者、执行模式、UTC 时间、协议与题目哈希、外部题目绑定状态。
3. **实验设计与覆盖**：冻结参数、原问题、随机种子、全局预算、各项目实际状态。
4. **资源与时间**：预留调用、训练／最终评估／轨迹调用、尝试／接受样本、无完整结果作业及 QPU 时间缺失；未知测量数据不填零。
5. **专项结果**：指标定义、单位、方向、有效 n、缺失 n、均值、中位数、样本标准差及极值；各次重复、演化轨迹和完整训练轨迹。
6. **证据索引与异常**：每个任务 ID、阶段、状态、样本数、客户端时间、缓解／后选择声明以及故障与取消状态。
7. **解释与复测**：有限样本偏差、参考可信度、缺口、当前不能支持的结论及下一轮计划。
8. **机器读取**：报告内置原始 JSON 证据，能够脱离原运行目录重新验收。

报告不自动编造设备性能结论。协议未定义质量阈值时，不写“测试合格”；缺少专业经典基线时不写“量子优势”；未取得实际测量时保留缺失状态。

## 2. 九类详细模板

模板目录为 `docs/report-templates/`，每个模板均含元数据、配置、原问题、实验设计、指标合同、逐次结果、统计、资源、异常、复核及附件要求。

| 模板 | 专项内容 | 当前自动化状态 |
| --- | --- | --- |
| 01 单机总报告 | L0/L1/L2 覆盖与完整系统配置 | 自动汇总当前已执行项目 |
| 02 哈密顿量模拟 | 模型、初态、时空网格、映射、轨迹误差 | 自动填充静态 Ising 样例；其他模型待扩展 |
| 03 玻色采样 | Fock/GBS、网络、探测、损耗、分布、吞吐 | 自动填充 Fock 样例；GBS 未实现 |
| 04 优化 | 原图、映射、可行解、目标值、训练、后处理、消融 | 自动填充 MIS-QAOA；原子原生及消融待扩展 |
| 05 VQE | 分子模型、ansatz、优化、测量、最终能量、曲线 | 自动填充两比特联调样例；正式分子基准未实现 |
| 06 材料动力学 | 关联、结构因子、误差分解、可信时间窗口 | 自动填充 1D Ising 链联调样例；完整材料套件未实现 |
| 07 分类 | 数据划分、模型选择、预测、混淆矩阵、基线、消融 | 设计模板；执行插件未实现 |
| 08 光子应用 | 稠密子图／振电谱的准入、完整求解和经典比较 | 设计模板；执行插件未实现 |
| 09 综合对比 | 导入、去重、可比性分组、指标、资源、审计 | 已实现报告批量读取与对比 |

手填设计模板不自动变为已验收结果。它们用于协议评审和后续插件开发；当前执行器只填充已经存在的任务指标。

## 3. 生成单机报告

```powershell
.\.venv\Scripts\qtest report runs/organizer-demo `
  --expected-suite examples/smoke-suite.json `
  --output reports/organizer-demo.md --force
```

运行器首先验证原始证据并重放算法，再输出：

- `organizer-demo.md`：可读报告，附带隐藏的机器证据块。
- `organizer-demo.report.json`：相同机器数据，适合程序集成。

两份文件内容互相独立；只复制其中一份到对比目录即可。`--force` 允许明确重新生成该报告及伴随文件，不改变原始运行。未提供该选项时拒绝覆盖。

输入也可以是厂商返回的结果 ZIP。`--expected-suite` 必须来自主办方事先保留的题目，而不是从待验收报告里复制出来的副本。

## 4. 批量生成综合对比

```powershell
# 扫描整个报告目录及子目录；建议输出至独立 analysis 目录。
.\.venv\Scripts\qtest compare reports --recursive `
  --expected-suite examples/smoke-suite.json `
  --output reports/comparison.md --force

# 多个输入可混用：单独报告、完整原始运行目录、厂商结果 ZIP。
.\.venv\Scripts\qtest compare reports/organizer-demo.md packages/result-v1.zip `
  --expected-suite examples/smoke-suite.json `
  --output reports/comparison-selected.md
```

| 选项 | 行为 |
| --- | --- |
| 一个或多个 inputs | 接受 Markdown、机器 JSON、运行目录、结果 ZIP 或报告文件夹 |
| `--recursive` | 对报告文件夹递归扫描；默认仅扫描直接子文件 |
| `--expected-suite` | 全部输入绑定同一份可信外部题目；跨不同题库比较时省略，按报告内协议拆组 |
| `--strict` | 任何候选报告被拒绝都不生成输出，适合正式验收 |
| `--force` | 更新已有的综合报告；不能借此覆盖来源测试报告 |

目录扫描读取 `.md`、`.json` 和 `.zip`。非测试文档及历史综合输出列入忽略清单；损坏或旧版测试报告列入拒绝清单。上限为每次 500 个候选文件；单份机器报告最多 80 MiB，原始证据仍受 50 MiB 的包限制。大型正式采样数据需要后续流式归档协议。

## 5. 对比逻辑

### 5.1 导入和去重

1. 校验报告结构、内容哈希和原始证据路径。
2. 以原始题目重放算法控制器，检查每次请求、测量计数和最终指标。
3. 按 run_id 与原始证据摘要去重。Markdown、JSON 和 ZIP 的同一运行只计一次。
4. 同一 run_id 出现不同证据时，整个比较停止，不能按文件顺序挑选一份。
5. 对正常导入的各次运行分别汇总；同一设备多个 run_id 不冒充多台设备，不自动合并重复样本。

报告内的“已绑定题目”只是原报告的声明；只有当前比较再次提供 `--expected-suite`，才建立本次外部绑定。设备身份始终由适配器声明，仍需硬件来源审核。

### 5.2 相同条件分组

每个条件组具有以下一致项：

- 协议版本、指标规则版本、benchmark ID。
- 原问题、算法参数、case_id、每调用 shots、计划重复数。
- suite 种子与全局调用／shots／墙钟／轮询预算。
- QPU 或模拟器类型。
- 结果中的缓解和后选择声明。

case_id 参与种子推导，因此不同 ID 即使参数相同也不会贸然合并。全局预算按原值分组，当前策略较保守。不同 SDK、技术路线与执行模式允许在同一语义条件组展示，并在来源表中披露；不同实例或预算的结果则分别显示。模型映射能力仍以冻结协议和适配器验收为准。

失败作业或不支持项目没有分数。后选择／缓解声明缺失的项目可以保留展示，但不进入“组内观测最佳”摘要。当前协议为固定算法轨道，不将尚未实现的开放算法轨道混入。

### 5.3 指标与结论

| 指标类别 | 比较方式 |
| --- | --- |
| 占据数误差、经验 TVD、最终能量绝对误差 | 越低越好，保留样本量与误差解释 |
| 可行率、最优解比例、最优比、接受率 | 越高越好，但需联合质量、资源及筛选规则 |
| 原始能量、碰撞概率、标准误 | 依任务解释，不自动排序 |
| 精确最优值、参考基态能量 | 参考元数据，不作为设备成绩 |
| 未注册的新指标 | 展示原始统计，不猜测方向或纳入最佳摘要 |

至少两个同条件、全部计划重复完成、该指标无缺失的运行，才产生观测最佳均值摘要。并列最佳保留全部运行。差值为与最佳均值之间的绝对差，不在参考值为零时计算百分比。该摘要不包含显著性检验，不意味着统计优越性或量子优势。

统计使用各次完成重复的数值，不平均训练过程或演化时间点来增加独立 n。n=1 的重复间标准差缺失。原始能量不按越低越好排序，以防将采样造成的低于真实基态误判为优秀结果。

## 6. 综合输出文件

| 文件 | 内容 |
| --- | --- |
| `comparison.md` | 摘要、系统来源、条件分组、逐指标对比、资源清单、限制、复测建议、完整导入审计 |
| `comparison.comparison.json` | 来源、分组规则、各运行统计、观测最佳、去重／拒绝／忽略清单，便于下游系统使用 |
| `comparison.comparison.csv` | 每个“条件组 × 运行 × 指标”一行，含 n、缺失、均值、标准差、极值；无分数项目见 JSON/Markdown 覆盖表 |

综合报告输出不重新作为测试输入；同目录重跑不会递归叠加旧统计。CSV 对可能被表格软件解释成公式的字符串作前缀处理，数值保持数值形式。

目前资源表展示各运行的全局开销；不同题库或时间口径不自动计算加速比，也不将 QPU 时间缺失视为零。长期稳定性及专业经典性能基线尚无完整数据。

综合 JSON 的 `resources.incomplete_jobs` 表示“没有取得状态为 completed 且符合测量合同的完整结果的作业数量”。该字段包含失败、取消、返回不合规数据等情形，不等于仍在运行的任务数；具体状态保留在原始证据中。消费综合 JSON 的下游程序应使用 `qtest-comparison-2` 格式。机器测试报告的证据格式保持 `qtest-report-1`。

## 7. 机器数据合同

JSON 顶层包含：

```json
{
  "format": "qtest-report-1",
  "sha256": "对 payload 规范化 JSON 的 SHA-256",
  "payload": {
    "declared_expected_suite_sha256": "原报告声明绑定的题目哈希，未绑定则为 null",
    "evidence": {
      "suite.json": {},
      "run.json": {},
      "observations/000001.json": {}
    }
  }
}
```

以上空对象仅示意形状，实际必须是通过各自合同验证的数据。Markdown 在末尾的 `QTEST_REPORT_V1` 注释中保存同一 JSON 的 Base64 编码；完整证据不依赖文件路径、网络或外部存储。

工具直接读取证据块，不解析展示表格。手动修改正文不会改变计算依据；正式修订请保留原始证据并重新生成报告。哈希用于发现内容变化，不是身份签名。

**分享这种自包含 Markdown 就会同时分享原始请求、计数和任务元数据。** 隐藏显示不等于脱敏；若需对外公开，应按项目的数据公开约定生成可公开证据，不能只删可见表格而保留隐藏块。

## 8. 旧报告升级与错误处理

0.1.0 的 Markdown 没有足够的机器数据，无法可靠还原模型、预算或原始测量。用保留的运行目录或结果 ZIP 重新执行 `qtest report ... --force` 即可升级；原始任务无需重跑。若只剩旧表格而无原始证据，工具明确拒绝，不猜测缺失配置。

| 退出码 | 含义 |
| --- | --- |
| 0 | 成功生成；不意味着设备质量达标或所有计划项目完成 |
| 2 | 无有效输入、严格模式拒绝、同 ID 冲突、配置错误或输出保护；不生成新的成功报告 |
| 3 | 有效报告已生成，但有输入被拒绝；输出中明确标为部分导入 |

正式发布建议使用 `--strict` 并保留本次主办方题目。常规分析可保留默认的部分导入方式，逐项处理拒绝原因后重跑。设备运行失败本身不等于报告文件无效：只要证据完整，失败项目仍可进入覆盖与资源分析。
